# nimbus-core audit report — v0.17

Scope: all twelve crates (`nimbus-replica`, `nimbus-bridge`, `nimbus-sig`, `nimbus-hash`, `nimbus-match`, `nimbus-order`, `nimbus-pipeline`,
`nimbus-journal`, `nimbus-sdk`, `nimbus-signer`, `nimbus-feed`, `nimbus-lightclient`). Method: automated tooling,
property-based, differential and end-to-end testing, mutation checks of the tests, an independent re-implementation
of the hash-input layouts from the whitepaper's table, manual review. This is an internal engineering audit, not a
third-party security audit; commission one before handling real value.

## Domain registry (hash inputs and signed messages)
0x00 batch leaf · 0x01 batch node · 0x02 header · 0x03 skip · 0x04 history leaf · 0x05 history node ·
0x06 state leaf · 0x07 state node · 0x08 timeout · 0x09 client order · 0x0A feed attestation · 0x0B journal link ·
0x0C engine checkpoint · 0x0D receipt leaf · 0x0E receipt node · 0x0F account action · 0x10 bridge operation ·
0x11 replication statement (ship / ack / hello) · 0x12 replay snapshot (local integrity seal).
Byte layouts: whitepaper Appendix B, Lemma 9″. Cross-domain signatures are tested to fail.

| P3 | Perf: journal was the longest branch | Variable-length records: an order record is 207 B (was 240 B). Journal share of time at 4 threads 33–35 % (was 39–40 %). End to end 120,000–130,000 entries/s on 4 threads with 2-of-3 bridge signatures and post-trade balances in every receipt. |

## Post-trade balances (v0.6)
Every receipt carries the account's balance in that market right after the change (base/quote, free/locked), so an
agent reconciles each trade exactly from the receipt alone. Checked against the sequential reference for every
admitted entry and every expiry in every test run.

## Design decisions recorded
* **ZIP-215 over RFC 8032 cofactorless**: the only way to make batch verification agree exactly with single
  verification. It accepts slightly more signatures than cofactorless verification, but only ones the key holder can
  produce; weak keys, which would let anyone sign, are excluded by `CheckedKey`.
* **Randomised batch coefficients**: a batch accepts an invalid set with probability < 2⁻¹²⁸; replay needs no
  particular batching (whitepaper Proposition Z).
* **Throughput vs latency batching**: a lone signature costs 70 µs here, 16 in a batch 33 µs each, 4,096 in a batch
  18 µs each. Large slots batch (`min_batch = 16`); sub-millisecond slots spread singles (`min_batch = 1`).
* **Journal ∥ matching**: matching runs while the slot's journal write and fsync are in flight; nothing is released
  until both finish; a failed journal write poisons the pipeline (restart replays the durable journal).
* **Checkpoints are not fsynced**: Ed25519 signing is deterministic, so recovery re-derives every checkpoint
  bit-identically from the journal.
